# Changelog

All notable changes to `bagisto/bagisto-api` are documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Added
- Storefront product cards (REST `GET /api/shop/products`, GraphQL `products`, and the product embedded in wishlist and compare items) carry `isSaleable`, `onSale`, `averageRating`, `totalRating` and `reviewsCount`, as the storefront card shows them; GraphQL `product` resolves the same fields. The review figures are loaded with the page, not per product.
- REST `GET /api/shop/products/{id}` carries `guestCheckout`, `visibleIndividually`, `onSale`, the review summary, `additionalAttributes` (the attributes shown in the storefront's specification table), `customerGroupOffers` (the customer group's quantity offers) and, for a configurable product, `configurableConfig` (the option configuration the storefront's option picker reads).
- REST `GET /api/shop/customer-profile` and GraphQL `readCustomerProfile` return the customer's group: `customerGroupId`, `customerGroupCode` and `customerGroupName`.
- Customer downloadable products carry `orderNumber`, the increment ID of the order they were bought with, as the storefront's downloads grid shows it.
- Returnable items (REST `GET /api/shop/returnable-items`, GraphQL) carry `qtyShipped`, `qtyInvoiced`, `qtyRefunded`, `qtyCanceled` and `orderStatus`.
- Admin customer cart, compare and wishlist items carry what core's customer panels show: `type`, `isSaleable`, `qtyAvailable` and `isOptionsRequired` on each, and on cart items `cartId`, the incl-tax unit price and row total, `options` and `productImage`.
- Admin order detail (REST `GET /api/admin/orders/{id}`) carries the totals core's order view shows: `subTotalInclTax`, `shippingAmountInclTax` (each also formatted), `baseShippingAmount`, `baseTaxAmount`, `baseDiscountAmount`, `baseGrandTotalInvoiced` and `baseGrandTotalRefunded`. GraphQL `adminOrderDetail` already exposed the columns.
- Admin GDPR requests carry `typeLabel` (`Delete` or `Edit`), the label core's GDPR grid shows next to the raw `type`.
- RMA file downloads for the admin API, as the admin panel serves them: REST `GET /api/admin/rma/requests/images/{id}` streams a return image inline and REST `GET /api/admin/rma/messages/{id}/attachment` downloads a message attachment under its original name. Both need `sales.rma.requests`, are REST-only binary responses (`Accept: application/octet-stream`), and also serve files stored on the public disk by earlier versions. The `images[].url` of `GET /api/admin/rma/requests/{id}` (GraphQL `adminReturn`) and the `attachmentUrl` of the RMA messages now point at these endpoints instead of a `/storage/...` link that returned 404 for privately stored files; the field names are unchanged.
- The RMA create form's order picker through REST `GET /api/admin/rma/requests/orders` and GraphQL `adminReturnableOrders`, reusing core's `OrderRMADataGrid` query: orders that can still have a return opened, with id, increment id, customer name, status, payment method, grand total and date filters. Needs `sales.rma.requests.create`, as core's create route does.
- Storage for admin API login sessions and API tokens: the `admin_api_sessions`, `admin_api_refresh_tokens`, `admin_api_tokens` and `admin_api_two_factor_challenges` tables, and `token_kind` and `channel` columns on `admin_api_audits` (existing rows that carry a token get `token_kind = integration`). Access tokens and API tokens are ES256-signed JWTs with a `kid` header; `php artisan bagisto-api:jwt-keys` creates the key pair under `storage/app/private/bagisto-api/jwt/` (or reads `BAGISTO_API_JWT_PRIVATE_KEY` / `BAGISTO_API_JWT_PUBLIC_KEY`), `--rotate` makes a new signing key while keeping the old public key for verification, and `--reissue-api-tokens` signs active API tokens again with the current key. `php artisan bagisto-api:prune-admin-tokens`, scheduled hourly, deletes expired refresh tokens, sessions ended more than 30 days ago and retired keys nothing valid is signed with. *Configuration → API → Admin Authentication* sets the access token (5–60 minutes, default 15), refresh token (1–90 days, default 30) and absolute session (1–365 days, default 90) lifetimes, the per-admin and per-API-token rate limits, the password-change revocation switches, no-expiry API tokens and the domain binding mode (`dns` or `origin`).
- Admin API login with access and refresh tokens, over REST and GraphQL alike: `POST /api/admin/auth/login` (GraphQL `createAdminLogin`) checks the email and password through core's `admins` provider and returns an ES256 JWT access token, an opaque refresh token, the session, the admin and the role's permissions; `POST /api/admin/auth/refresh` (`createAdminTokenRefresh`) rotates both tokens, and a refresh token that was already used revokes the whole session; `POST /api/admin/auth/logout` (`createAdminLogout`) and `POST /api/admin/auth/logout-all` (`createAdminLogoutAll`) end the current session or every session. Login takes an optional `device_name` and `client_type` (`web`, `mobile`, `pos`, `desktop` or `other`). Five failed logins per email and address in a minute lock the login for that minute (429 with `Retry-After`); wrong credentials and inactive admins get core's messages, and Laravel's `Attempting`, `Failed`, `Lockout`, `Login` and `Logout` events fire for the `admin-api` guard. When the admin has two-factor authentication enabled (and set up), login answers `202` with `twoFactorRequired: true` and a single-use `challengeToken` valid for 5 minutes instead of tokens.
- Admin API two-factor login: `POST /api/admin/auth/two-factor` (GraphQL `createAdminTwoFactorVerify`) exchanges the challenge token and the 6-digit authenticator `code`, or a `backupCode`, for the token pair, through core's `two_factor_authentication()` helper. A code from an already used time window is refused, a backup code is used up, five wrong codes revoke the challenge (`two_factor_challenge_invalid`), and five wrong codes a minute for the same admin are answered with `429`. Expired challenges are deleted by `bagisto-api:prune-admin-tokens`.
- Admin API password reset: `POST /api/admin/auth/forgot-password` (`createAdminForgotPassword`) sends core's admin reset email and gives the same answer whether or not the email exists; `POST /api/admin/auth/reset-password` (`createAdminResetPassword`) sets the new password with the emailed token through core's `admins` password broker, drops the admin's web sessions as core does, and revokes every API session (and every API token when *Revoke API Tokens on Password Change* is on). Each allows five requests a minute per client address (`429` with `too_many_password_requests`).
- `PUT /api/admin/account` (GraphQL `createAdminAccountUpdate`) updates the signed-in admin's name, email and password as the *My Account* screen does, requires `current_password` (`422` with `invalid_current_password` when it is wrong), fires core's `admin.password.update.after` on a password change and answers with `revokedSessions` and `revokedApiTokens`. It needs a login session's access token.
- API sessions are revoked automatically, whichever screen or endpoint made the change: a password change ends the admin's other sessions when *Revoke Sessions on Password Change* is on (the default) and their API tokens when *Revoke API Tokens on Password Change* is on (off by default); deactivating an admin ends their sessions, while their API tokens are refused until the admin is active again; deleting an admin deletes both. Pending two-factor challenges are revoked by each of these.
- Admin API sessions: `GET /api/admin/auth/sessions` (`adminSessions`) and `DELETE /api/admin/auth/sessions/{id}` (`deleteAdminSession`) list and revoke the caller's own sessions; `GET /api/admin/settings/users/{id}/sessions` (`adminSettingsUserSessions`) and `GET /api/admin/settings/api-sessions` (`adminApiSessions`) list another admin's or every admin's sessions under the new `settings.api_sessions` ACL key, and `POST /api/admin/settings/users/{id}/revoke-sessions` (`revokeSessionsAdminSettingsUser`) revokes all of an admin's sessions under `settings.api_sessions.delete`. Each session records its last address, user agent, channel (`rest` or `graphql`) and use, written at most once a minute unless the address changes.
- *Settings → API Tokens* in the admin panel: API tokens for server integrations, each acting as one admin user with that admin's role permissions and bound to one domain. The create form takes a name, the admin user (yourself by default), the domain (a URL is reduced to its lower-case host, international names become punycode, IP addresses and wildcards are refused) and an expiry date or, after a confirmation, no expiry (unless *Allow API Tokens Without Expiry* is off). The token is shown once, with a copy button; afterwards only its last characters are kept. The listing shows the admin, domain, expiry, last use, address and channel, status and creator, filterable by each; a token can be renamed and revoked, and revoked tokens stay listed. New ACL keys `settings.api_tokens`, `settings.api_tokens.create` (which also covers renaming), `settings.api_tokens.delete` and `settings.api_tokens.manage_others`; without the last one an admin sees and manages only their own tokens. `php artisan bagisto-api:api-token:create --admin= --name= --domain= [--expires=YYYY-MM-DD|never] [--only-token]` creates one from the console and prints it once. Creating, renaming and revoking fire `bagistoapi.admin.api-token.{create,update,revoke}.before/after` and are written to the audit trail, with the channel `panel` or `cli`.
- API tokens over the API, list, read and revoke only (creation stays in the panel and the console): `GET /api/admin/settings/api-tokens` (GraphQL `adminApiTokens`, filters `admin_id`, `status`, `domain`), `GET /api/admin/settings/api-tokens/{id}` (`adminApiToken`) and `DELETE /api/admin/settings/api-tokens/{id}` (`deleteAdminApiToken`; `409` when already revoked), under `settings.api_tokens` / `settings.api_tokens.delete`, and another admin's tokens only with `settings.api_tokens.manage_others`. The token string is never returned.
- *Settings → API Sessions* in the admin panel lists every admin's login sessions with device name, client type, login and last address and user agent, last use and channel, refresh and absolute expiry and status, filterable by admin, client type and status, and revokes one session or every session of an admin (`settings.api_sessions`, `settings.api_sessions.delete`).
- `GET /api/admin/get` and `readAdminProfile` return `tokenKind` (`session` or `api_token`), `tokenId` and `tokenExpiresAt`.
- The Postman admin collection gains an **Auth** folder, in the order a client uses it (login, two-factor, refresh, profile, sessions, revoke a session, logout, logout of every session, forgot and reset password, account update), and **Settings → API Tokens** and **Settings → API Sessions** folders. The login, two-factor and refresh requests, REST and GraphQL, store the tokens in the environment; a login that needs a second factor stores its challenge token in the collection variable `adminChallengeToken`, which the two-factor request sends. A collection-level pre-request script refreshes the access token when its `exp` is less than a minute away, unless `adminApiToken` is set, in which case that token is sent instead.
- Authentication events (login, failed login, lockout, two-factor challenge and wrong code, refresh, refresh token reuse, logout, logout of every session, session revocation, automatic revocation, password reset request and reset, account update and API token domain mismatches) are written to the admin API audit trail with their token kind and channel, and audited writes now record the token kind and channel of the request.
- *Configuration → API → Admin Authentication* gains a **Login Protection** group (failed logins before the lockout, 3–20, default 5; lockout time, 60–3600 seconds, default 60; two-factor challenge lifetime, 1–15 minutes, default 5; wrong two-factor codes per admin per minute, 3–20, default 5; forgot and reset password requests per address per minute, 1–20, default 5), a **Data Retention** group (days ended sessions are kept, 1–365, default 30; days the API audit history is kept, 0–3650, empty or 0 keeps it forever, falling back to `BAGISTO_API_AUDIT_RETENTION_DAYS`) and, under **Rate Limits**, the requests per minute allowed without a token per address (10–1000, default 60). Each value replaces one that was hard-coded or set only in the package config file, and keeps that value as its default. `bagisto-api:prune-audits` reads the retention setting and is now scheduled daily.
- Storage for storefront customer login sessions, the groundwork for customer access and refresh tokens: the `customer_api_sessions` and `customer_api_refresh_tokens` tables (sessions belong to one customer and one channel and are deleted with either), ES256 customer access tokens (`typ: customer_access`, `aud: bagisto-shop-api`) signed with the same keys as the admin API's and refused on the admin surface, as admin tokens are refused on the storefront, and rotating refresh tokens with reuse detection. `php artisan bagisto-api:prune-customer-tokens`, scheduled hourly, deletes expired refresh tokens and long-ended sessions. *Configuration → API → Customer Authentication* sets the access token (5–60 minutes, default 15), refresh token (1–90 days, default 30) and absolute session (1–365 days, default 90) lifetimes, the most live sessions per customer (0–100, default 0 for no limit), the login attempts and lockout, the token refreshes per session, the requests per signed-in customer, whether a password change ends the other sessions, and how long ended sessions are kept. Customer login, registration and social login issue these tokens (see below).
- Storefront customer sessions over REST and GraphQL: `POST /api/shop/customer/refresh` (`createCustomerTokenRefresh`) exchanges a refresh token for a new pair, and a refresh token presented twice ends its whole session; `POST /api/shop/customer/logout-all` (`createCustomerLogoutAll`) ends every session; `GET /api/shop/customer/sessions` (`customerSessions`) lists the customer's live sessions with `isCurrent`, and `DELETE /api/shop/customer/sessions/{id}` (`deleteCustomerSession`) ends one. Login takes an optional `device_name` and `client_type`. Failed logins are limited per email and address, refreshes per session and requests per signed-in customer, each answered with `429` and `Retry-After`. A customer's sessions end when their password changes (unless *Revoke Sessions on Password Change* is off), when it is reset, and when the customer is deactivated or deleted, from any screen.
- *Customers → API Sessions* in the admin panel lists every customer's storefront login sessions with the customer, device name, client type, channel, login and last address and user agent, last use, refresh and absolute expiry and status, filterable by each, and ends one session or every session of a customer; the customer page shows a card with that customer's live sessions and a button to end them all. Over the API, `GET /api/admin/customers/api-sessions` (GraphQL `adminCustomerApiSessions`, filters `customer_id`, `client_type`, `channel_id`), `GET /api/admin/customers/{id}/api-sessions`, `DELETE /api/admin/customers/api-sessions/{id}` (`deleteAdminCustomerApiSession`) and `POST /api/admin/customers/{id}/revoke-api-sessions` (`createAdminCustomerApiSessionRevoke`, answering with `revoked`). New ACL keys `customers.api_sessions` and `customers.api_sessions.delete`.
- Storefront authentication events (login, failed login including inactive and unverified accounts, lockout, refresh, refresh token reuse, logout, logout of every session, session revocation by the customer or an admin, and automatic revocation on a password change, reset or deactivation) are written to the admin API audit trail with the token kind `customer_session`, the customer as the user and, when an admin ended the session, the admin's name.
- Customer login merges a guest cart: `POST /api/shop/customer/login` takes an optional `guest_cart_token` (GraphQL `guestCartToken`) and, when it still names an open guest cart, merges that cart into the customer's cart in the same transaction as the session, as `POST /api/shop/merge-carts` does, and returns the customer's cart id in the new `cartId` field. A token that names no open guest cart is ignored and `cartId` is `null`. Core's `customer.after.login` fires once afterwards without merging the cart a second time.
- A storefront request whose bearer is a customer access token that is expired, revoked, of another channel or forged is answered before the operation runs with `401` and `access_token_expired` or `unauthenticated` (REST `error`, GraphQL `extensions.code`), on every storefront operation. Before, these answered `401` or `403` without a code, or ran as a guest. The login, registration, social login, refresh and password operations never refuse a stale bearer.
- The storefront sign-in operations (login, registration, social login, refresh, token verification, logout, logout of every session, sessions, password reset and account verification) have their own **Customer Authentication** tag in Swagger and a **Customer Auth** folder in the Postman shop collection, in the order a client uses them. The shop collection stores the customer token pair from the login, registration, social login and refresh requests, REST and GraphQL, and a collection-level pre-request script refreshes the access token when its `exp` is less than a minute away.
- `docs/authentication.md` documents the customer flow: login, refresh and reuse detection, logout and sessions, the guest cart merge, the error codes, the configuration fields, client notes, and the steps for apps that used the Sanctum token. The README summarises it.

### Changed
- **Breaking:** GraphQL types numeric and boolean fields by their real type instead of `String`. A field backed by a model accessor that returns an integer, a float or a boolean is now `Int`, `Float` or `Boolean`, so `featured` answers `false` instead of `""`, `price` answers `24.99` instead of `"24.99"`, and the `0`/`1` flags (`isInWishlist`, `isInCompare`, `onSale`, `hasDraft`, `isPinned`) answer numbers. 83 fields change across the storefront and admin schemas (for example `Product.price`, `Product.status`, `Product.isSaleable`, `Category.maxPrice`). REST already returned these values typed and is unchanged. A client that compared against the old strings must compare against the typed values.
- **Breaking:** the API no longer fires `order.created.after`, `cart.before.add` and `cart.after.add`, events core never fires and nothing in core listens to. Placing an order and adding to the cart fire core's own events (`checkout.order.save.before/after`, `checkout.cart.add.before/after`), so a listener should use those.
- **Breaking:** applying a coupon (REST `POST /api/shop/apply-coupon`, GraphQL `createApplyCoupon`) answers as the storefront does: an unknown code, the code the cart already carries, and a code that does not apply to the cart are refused with `422` and core's coupon message (GraphQL reports them in `errors[]`), instead of `201` with `success: false`.
- **Breaking:** reading one admin product, its inventories, one category or one review (REST `GET /api/admin/catalog/products/{id}`, `/catalog/products/{productId}/inventories`, `/catalog/categories/{id}`, `/customers/reviews/{id}`, GraphQL `adminCatalogProduct`, `adminCatalogProductInventories`, `adminCategory`, `adminCustomerReview`) needs `catalog.products.edit`, `catalog.categories.edit` or `customers.reviews.edit`, as core opens them only on the edit screen. The listings keep the list permission. The GraphQL product detail checked no permission at all before.
- **Breaking:** cart and checkout client errors answer with a 4xx instead of `500` (the REST status; GraphQL reports them in `errors[]` as before):
  - a refused add-to-cart or quantity update (missing options, not enough stock) answers `400`, as the storefront's cart does;
  - a missing or invalid checkout address, shipping method or payment method, an empty cart, an unmet minimum order amount and a missing email answer `422`;
  - a suspended or inactive account, and guest checkout on a cart that does not allow it, answer `403`.

  Only real server failures still answer `500`.
- **Breaking:** storefront customers authenticate with ES256 JWT access tokens instead of Laravel Sanctum tokens. `POST /api/shop/customer/login` (`createCustomerLogin`), `POST /api/shop/customers` and `POST /api/shop/customers/social-login` return `tokenType`, `accessToken`, `expiresIn`, `accessTokenExpiresAt`, `refreshToken`, `refreshTokenExpiresAt`, `session` and `customer`; `token` still carries the access token for one release. A migration deletes the customers' Sanctum tokens, so every customer logs in again after the upgrade. An access token works only on the channel it was issued on, and admin tokens and customer tokens are refused on each other's surface.
- **Breaking:** a refused customer login is an error instead of `201` with `success: false`: `401 invalid_credentials` for a wrong email or password, `403 account_inactive`, `403 account_unverified`, and `429 too_many_login_attempts`. REST bodies carry the code in `error`, GraphQL errors in `extensions.code`.
- `POST /api/shop/customer/logout` ends only the session of the access token sent. `POST /api/shop/verify-tokens` (`createVerifyToken`) also returns `sessionId` and `sessionExpiresAt`.
- The per-minute request limits for signed-in admins and API tokens now have an upper bound of 100000; a saved value above it is used as 100000.
- The security headers the API adds follow `api-platform.security_headers`: `enabled` turns them off and `csp_header` sets the Content-Security-Policy. The middleware read these keys from the wrong place, so the configured values never applied. Core's own security headers (`X-Frame-Options`, `Referrer-Policy`, `Strict-Transport-Security`) are sent by Bagisto on every response either way, so `force_https` has no visible effect.
- Documentation: a new authentication guide, [`docs/authentication.md`](docs/authentication.md), covers both surfaces as they work today — the admin login, two-factor, refresh and refresh token reuse detection, logout and sessions, password reset and account update, API tokens with their domain binding and the trusted-proxy caveat, the configuration fields, every error code, and the storefront key, customer token and guest cart token — with sequence diagrams, curl and GraphQL examples and client notes (secure storage, single-flight refresh, retry on `access_token_expired`). The README links to it and its admin authentication section now lists every error code; the Postman collection descriptions carry the same flow guide and link, and the storefront key is documented as coming from `.env` or `bagisto-api:generate-key`, not from an admin screen.
- Documentation: every REST operation in the OpenAPI documents now has a summary and a description of its own; about a hundred operations only repeated their summary, and the storefront customer order, invoice, shipment and downloadable-product reads showed API Platform's generated text. `GET /api/shop/payment-methods` now documents that a missing or unknown cart token answers `404`, not `401`.
- **Breaking:** the admin API accepts only JWT access tokens from a login and JWT API tokens; Integration tokens (`<id>|<secret>`) no longer authenticate. Every request is authorised by the admin's role permissions alone. An expired access token is answered with `401` and `access_token_expired`, an invalid token or revoked session with `401` and `unauthenticated`, an unusable refresh token with `401` and `refresh_token_invalid`, an expired or revoked API token with `401` and `api_token_expired` / `api_token_revoked`, and an API token used from a domain it is not bound to (by DNS or, when configured, by `Origin`) with `403` and `api_token_domain_mismatch`. REST bodies carry the code in `error`, GraphQL errors in `extensions.code`. The login, two-factor, refresh, forgot-password and reset-password operations are the only admin operations reachable without a token.
- The admin API audit history stores the request URL without its query string, so a secret passed there never reaches the audit table.
- Admin API rate limits apply per admin for login sessions and per API token for API tokens, from *Configuration → API → Admin Authentication*.
- **Breaking:** the Postman environment replaces `adminToken` with `adminEmail`, `adminPassword`, `adminAccessToken`, `adminRefreshToken`, `adminAccessTokenExpiresAt` and `adminApiToken`; import it again.
- The admin API change history moved from *Settings → Integration → History* to *Settings → API Audit* (`admin/settings/api-audit`), under the new ACL keys `settings.api_audit` (list and detail) and `settings.api_audit.delete` (mass delete and clean-up). Roles that held `integration.history` or `integration.history.delete` need the new keys. The listing gains the admin, token kind (`session`, `api_token`, or `integration` for rows written by the removed tokens), token, channel (`rest`, `graphql`, `panel`, `cli`), method and address columns with filters, and the detail page shows the token kind and channel.
- **Breaking:** an admin whose role lacks the permission for an order action gets `403` before any order-state rule is checked, instead of `422` after them: cancel (`sales.orders.cancel`), invoice (`sales.invoices.create`), ship (`sales.shipments.create`), refund and refund preview (`sales.refunds.create`) and reorder (`sales.orders.create`, now checked before the order is looked up). The messages are unchanged.
- **Breaking:** admin read permissions fail closed: a resource class with no entry in the admin permission map is refused with `403` instead of being open to any signed-in admin, and the RMA reason, status, rule and custom field processors and the return and return message processors refuse an operation they do not handle with `403` instead of handing it to the default persist processor.
- `php artisan bagisto-api-platform:install` creates the JWT signing keys (`bagisto-api:jwt-keys`) and prints the admin login endpoint (`/api/admin/auth/login`) and the *Settings → API Tokens* screen.
- On MySQL and MariaDB, model properties that the model does not cast now have the type PostgreSQL gives them and the published schema documents: `int`/`int unsigned` columns are `Int`/`integer` (they were `String` for unsigned columns), `tinyint(1)` columns are `Boolean`/`boolean` (they were `String`), and `decimal`, `timestamp`/`datetime`, `bigint` and `double` columns are `String`/`string` (decimals were `Float`/`number` and timestamps `date-time`). REST bodies are unchanged; GraphQL now serialises these fields by the declared type, so on MySQL a flag that came back as `"1"` comes back as `true`.
- Flag fields on attributes (`isRequired`, `isUnique`, `isFilterable`, `isConfigurable`, `isVisibleOnFront`, `isComparable`, `isUserDefined`, `valuePerLocale`, `valuePerChannel`, `enableWysiwyg`), categories (`status`, and `position` as an integer), bundle options (`isRequired`), bundle option products (`isUserDefined`, `isDefault`) and customizable options (`isRequired`) are cast as core casts them, so they are `true`/`false` on every database. On MySQL the GraphQL `Boolean!` fields returned the string `"1"` and REST returned `1`/`0`; PostgreSQL already returned booleans. This replaces the 2.5.0 entry that kept `0`/`1` for these resources.
- **Breaking:** the Postman environment replaces `customerToken` with `customerAccessToken`, `customerRefreshToken` and `customerAccessTokenExpiresAt`; import it again.
- **Breaking:** the storefront product listing without a sort (REST `GET /api/shop/products` with no `sort`, GraphQL `products` with no `sortKey`) is ordered by *Configuration → Catalog → Products → Storefront → Sort By*, as the storefront category page is, falling back to `price-desc`. Before, it was ordered by `id`.

### Removed
- **Breaking:** the storefront GraphQL query `categoryTrees`. It could only return each root's `id`; `treeCategories` returns the same nested tree with every category field. REST `GET /api/shop/category-trees` is unchanged.
- The unused `RateLimitApi` middleware (alias `api.rate-limit`, attached to no route), the `api-platform.rate_limit` configuration block and its `RATE_LIMIT_SKIP_LOCALHOST`, `RATE_LIMIT_AUTH`, `RATE_LIMIT_ADMIN`, `RATE_LIMIT_SHOP`, `RATE_LIMIT_GRAPHQL` and `RATE_LIMIT_CACHE` environment variables, none of which limited any request. The admin limits are set under *Configuration → API → Admin Authentication*, the storefront limit per storefront key. The unread `use_whitelist`, `protected_operations` and `messages` keys are removed from `config/graphql-auth.php`.
- **Breaking:** the Integration token flow: the *Settings → Integration* screens, the opaque `<id>|<secret>` tokens with their permission types (`all`, `custom`, `same_as_web`), per-token abilities and per-token rate limits, the IP allowlist, the token notification emails and their signed revoke links, the `admin.integration.*` routes, the `integration.*` ACL keys and menu entries, and the *Configuration → API → Integration* module switch. A migration drops the `admin_personal_access_tokens` table (its `down()` recreates it empty). Apps log in through `POST /api/admin/auth/login`; server integrations use an API token from *Settings → API Tokens*.
- **Breaking:** admin customer impersonation: REST `POST /api/admin/customers/{id}/impersonate` and GraphQL `createAdminCustomerImpersonate`, which issued a Sanctum token for the customer. Customer tokens are now login sessions bound to the customer's own credentials, and an admin acting with them would bypass the session, audit and revocation rules; there is no replacement.

### Fixed
- REST `GET /api/shop/products/{id}` no longer answers `500` on PostgreSQL for a product with a select attribute shown in the specification table: the option was looked up by its label instead of its id, which MySQL coerced silently and PostgreSQL refused.
- A token refresh (admin and customer) claims the refresh token and issues the new pair in one database transaction. A failure part way used to leave the token used with no replacement, so the client's retry was treated as reuse and ended the whole session; the retry now succeeds.
- Merging a guest cart, at login (`guest_cart_token`) or through the merge-cart operation, locks the guest cart first, so two concurrent requests cannot merge it twice; the second finds it merged. Each guest cart item is added in its own savepoint and skipped when it cannot be added, as core does, so a failed item no longer aborts the login transaction on PostgreSQL.
- A logout, logout-all or any other write sent with no body is accepted whatever its `Content-Type`; a bare `curl -X POST`, which sends `application/x-www-form-urlencoded`, got `415`.
- Expected authentication failures (an invalid or reused refresh token, an expired access token, a lockout) are answered with their 401, 403 or 429 and no longer written to the error log.
- The audit entry for an admin acting on a customer's API session stores the admin's id (`new_values.admin_id`) as well as their name.

### Security
- Refresh tokens rotate on every use and only their SHA-256 hash is stored; a refresh token presented a second time is treated as stolen, revokes its whole session and is audited. A session also ends at its absolute lifetime however often it is refreshed.
- Access tokens and API tokens are verified as ES256 only, with a known `kid`, so `alg: none`, HS256 signed with the public key and tokens signed by an unknown key are refused; neither kind carries an email, a name or any permission, so a role change or deactivation applies on the next request.
- API tokens are bound to one domain and checked on every request before any permission: in `dns` mode the client address must be one the domain resolves to (cached for 5 minutes), in `origin` mode the `Origin` or `Referer` host must match. A mismatch is refused with `403`, counted on the token and audited with the address seen. `dns` mode relies on the client address Laravel reports, so restrict the trusted proxies at the edge.
- Creating an API token for another admin needs `settings.api_tokens.manage_others` and is refused unless every permission of that admin's role is also held by the creator's role (a role with all permissions may create tokens for anyone), so a limited admin cannot mint a token that acts as a broader admin.
- Admin product image uploads (REST `POST /api/admin/catalog/products/{productId}/images`) are accepted only when both the type detected from the file's contents and the extension it was sent with are an allowed image type (bmp, jpeg, jpg, png, webp), so a JPEG named `x.php` or `x.html`, an SVG, or an HTML file named `x.png` is refused with 422. The image is re-encoded to webp and stored under a generated name in core's product directory (`products/{id}/<random>.webp`), as the admin panel stores it; a file that cannot be decoded as an image is refused with 422. The response fields are unchanged; only the stored `path` and `url` now end in `.webp`.
- Admin product video uploads (REST `POST /api/admin/catalog/products/{productId}/videos`) need both an allowed detected type and an allowed extension (mp4, webm, ogg, mov), and the file is stored under a generated name with the extension taken from its contents, never from the client, in core's product directory.
- HTML sent through the admin API is now run through core's `clean_content()` before it is saved, as the admin panel does: CMS page `html_content` (create, and the requested locale on update), email template `content` (create and update), category `description` (create and update, top level and every locale block) and every WYSIWYG textarea product attribute on product update. Script tags, Blade echoes and directives, and raw PHP are stripped over REST and GraphQL alike.
- The images archive of an admin import (REST `POST`/`PUT /api/admin/settings/data-transfer/imports`, `upload_images`) is no longer extracted whole. As in core, only image entries (bmp, gif, jpeg, jpg, png, webp) are unpacked, entry by entry, and entries whose names contain `..`, a backslash or a leading `/` are skipped. An archive with more than 5,000 entries or more than 1 GB unpacked is refused with 422 before the import is created.
- Files an admin attaches to an RMA message through REST `POST /api/admin/rma/messages` are stored on the `private` disk under `rmas/{rma}/conversations/{message}`, as core's admin panel stores them. They were saved on the default (public) disk under `rma-conversation/{message}`, where anyone could fetch them from `/storage/...`. Files stored by earlier versions stay where they are; see `UPGRADE.md`.

- GraphQL lookups by id return only approved reviews, enabled categories and products the storefront would show.

### Removed
- The report types dashboard `total-visitors`, customer report `customers-traffic` and product report `products-with-most-visits`. Core has no method behind them, so they returned 500. They now answer with the invalid-type error.

### Changed

- Deleting a customer account now needs the account password and is refused while the customer has pending or processing orders, as the storefront does.
- Registering with email verification on no longer returns a token for the unverified account. The response carries `token: null` and a `message` asking the customer to verify the email.
- Guest EU withdrawal lookups are limited to five attempts per minute for each address and order number.
- The public review list and single-review lookup return approved reviews only. A `status` filter from the client is ignored.
- A newsletter address that unsubscribed earlier can subscribe again.
- A throttled password reset reports that it is throttled instead of "email not found".
- Google social login is refused when no Google client id is configured, instead of skipping the audience check.
- Cart `taxAmount`, `baseTaxAmount` and `formattedTaxAmount` returned 0 and now carry the cart's tax.
- A coupon that reached its usage limit is removed from the cart and reported when the order is placed.
- Cancelling, closing or reopening a return follows the same rules as the storefront, including the return window.
- A role or admin update cannot remove the last all-access administrator, and changing an admin password fires the same event as the admin panel.
- Import stats and download use the `settings.data_transfer.imports.import` permission, as core does.
- Configuration values saved through the API are no longer written in clear text to the audit log, and any audited field whose name contains secret, password, key or token is redacted.
- The email link that revokes an integration token now opens a confirmation page and revokes only after a confirming click, so link scanners cannot revoke a token.
- The installer reports when it could not register the service provider instead of printing success.
- Request logging honours its configuration, uploaded multipart temp files are removed after the request, and query logging no longer records bindings or logs on local environments by default.
- Static customer `api_token` and `token` values are no longer accepted by the download mutation. Use the bearer token.
- The `first` argument is limited to 1–50 on every list. `first: 0` and `first: -1` return a one-item page, and a larger value is capped at 50.
- Pages assigned to another channel are no longer returned, and categories that are disabled or outside the channel root are no longer listed. The category tree starts at the channel's root category, and `depth` is limited to 1–6.
- The channel `allowedIps` field is no longer exposed.
- The product `cost` field and the downloadable link `url` and `fileName` fields are no longer exposed.
- A single product (REST `GET /api/shop/products/{id}`, GraphQL `product(id:)`, `product(sku:)`, `product(urlKey:)`) is returned only when the store front would show it: assigned to the channel, enabled, and visible individually. A product that is hidden from the catalog answers 404 and `product not found`. An enabled variant of a product that passes these checks can still be opened by id or SKU, so clients that fetch variants keep working. Variants are never listed.
- Sorting products by name works when a channel is passed.
- Internal clean-up with no change to any response: variables use full words, deeply nested methods were split, and the largest classes (cart processor, service provider, product model) were divided into focused parts.
- Removed an unused product provider that no endpoint called.
